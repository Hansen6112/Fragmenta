## 0. Bucket Review Rules (18 Nov, amend spec §4)

Settled against `tools/modifier_catalogue.md` at `99ab9f0` (Amendment 1 landed), checked row-by-row against each effect's real code and description. Full review: `fragmenta-combat-phase2-bucket-review.md`. Without these, the additive buckets below would double-count, or put things where they don't belong.

**Rule 1: "Upgrades" replace a value; they don't add to it.** Many set tiers *raise another effect's own number* (Crushing Impact 1.2 -> 1.35/1.4; Elemental Focus 1.08 -> 1.12/1.15/1.2; Spell Ward 0.9 -> 0.8; Ambush -> 1.7; Executioner's threshold 30% -> 40%; Surging Conduit charges 1 -> 2; the generic synergy 25% -> 40%). Today's code takes the **best** of them (`Math.max`/`Math.min`). Put into an additive bucket as separate entries, they'd **stack** instead (e.g. Crushing Impact +20% *plus* +35% = +55%, instead of +35%). These entries get `upgrades: "<base entry key>"` and set the base entry's `value` (or a named param, e.g. `threshold`/`charges`); the registry uses the **best** value among the base and its upgrades, and only the base entry adds to the bucket. Audit **M3** checks every `upgrades` target exists. Marked `**Upgrade**` in the tables below, not a bucket of their own.

**Rule 2: what goes in which bucket.**
- **burst** = **primed or limited-use** hits: first hit each fight, next hit after X, charges, every Nth hit.
- **conditional** = applies on **every hit that qualifies** (target below a health threshold, the hit is a counter, the hit is elemental, etc).
- **Crit chance isn't a damage bucket.** It's `stat.critChance` (or a behaviour that forces a crit). Only crit **damage** is the **crit** bucket.

**Rule 3: class mechanics stay outside the buckets**, same as an action's own `dmgMult`: elemental **synergy** (generic and curated combos) and damage-type **tags**. Gear that changes them (River Harmony, Pre-Kabal 6pc) is an **upgrade or behaviour on the mechanic**, not a bucket entry. Flat reductions (Thick Hide's `flatDamageReduction`, Armor Crack's flat ignore) stay flat and apply where they do today -- unaffected by this pass.

**§4 note (Fragmenta 6pc):** was dead since the damage-types switch went live (`09d4131` retired the matchup cycle it reads). Tyler's separate call (18 Nov) approved the bucket review's own §4 replacement -- **now implemented**, in its own commit, separate from 2d: `set:Fragmenta:6`, hook `calculateDamage.tags`, outside the buckets per Rule 3. ## 5. Worst-case stack per bucket today

**Outgoing damage** (verified against the spec's own §1/§4 example): Execution Protocol ×2 (burst), Temporal Echo ×2 (burst), Kingslayer ×1.25 (conditional), a crit ×1.5, Momentum at 5 stacks ×1.5 (stacking), Tempered Steel at 15 stacks ×1.3 (stacking), Threads of Consequence ×1.4 (burst) — legacy product **×20.5**, confirmed consistent with current `rollPlayerDamageCoreForPipeline` multiplier chain. Bucketed: conditional (Kingslayer +25% → ×1.25), stacking (Momentum +50% + Tempered Steel +30% = +80%, capped at +75% → ×1.75), burst (Execution Protocol +100% + Temporal Echo +100% + Threads of Consequence +40% = +240%, capped at +150% → ×2.5), crit ×1.5 → **×1.25 × 1.75 × 2.5 × 1.5 = ×8.2**, matching the spec exactly.

**Defense ignore** (corrected 14/16 Nov): `armor_crack` is **not** dead — js/data/sets.js:664-666 (`armorCrackAmount`) dispatches it, called from combat.js:2121/pipeline.js:1693, flat -2 Defense (-4 with Siege Corps 4pc). The other confirmed-live sources are unchanged: **Foreseen Strike** (×0.5 effective-Defense factor, every 3rd player action, combat.js:1453) and **Commanding Presence** (Regalia of the Crimson Vanguard 4pc; sets the effective-Defense multiplier to **0** outright, same every-3rd-action timing, combat.js:1894). Worst case today is still **Defense already fully ignored** (0), since Commanding Presence alone zeroes it regardless of whatever flat amount `armor_crack` also subtracts — the proposed -100% cap (§4) is already the ceiling the current code reaches, so R3's cap introduces no regression risk here. (`armor_crack` being alive doesn't change this conclusion — a flat subtraction from an already-zeroed value is still zero.)

**Incoming mitigation** (corrected 14/16/18 Nov): both **Spell Ward** and **Storm Barrier** are live. Two separate worst-case chains exist TODAY, not hypothetically post-R1/R2:
- **Player/ally-defense side** (js/data/actions.js ~505-520, ~610-626): **corrected 18 Nov -- the ×0.3 three-set stack (Stormwatch 6pc + Stonewarden 6pc) cannot be built.** Stonewarden and Stormwatch both top out at a 6pc tier, so holding both 6pc bonuses needs 12 equipped pieces; there are only 11 equip slots total (9 single slots + Trinkets' 2 -- Dual Focus/Pocket of Holding's extra trinket slot doesn't help, since Pocket of Holding itself occupies one of the slots it's unlocking). The real, buildable worst case is a **single full 6-piece Stormwatch set alone**: several of its own pieces already carry the `spell_ward` effect, so 6pc gets you Spell Ward's base (×0.9) enhanced to ×0.8 by its own 4pc bonus, AND Storm Barrier (×0.5, 6pc) on the first magical hit each fight -- `×0.8 × 0.5 = ×0.4`, a 60% reduction, landing exactly ON the proposed cap (§4's floor ×0.4), not past it. R3 introduces no regression here; this is the cap working as intended, not a violation.
- **Enemy-defense side** (js/engine/combat.js:2001, `rollPlayerDamage`'s `sangMit` chain): `sangCuDefenderMitigation(creature) × enemyOneHitMitigationMultiplier(creature) × enemyRepeatableMitigationMultiplier(creature) × enemyAllyProtectionMultiplier(state, creature)` — FOUR factors multiplied on the same hit, each up to ×0.9 (Smuggler's Guard/Commander's Poise can BOTH apply within the first factor alone, ×0.81), and the chain is generic over `creature` already (not player-hardcoded) and already reads `state.combat.enemies` for the ally-protection factor — so a single Sanguivorum creature wearing items from all four families today gets `0.81 × 0.9 × 0.9 × 0.9 = ×0.59` (-41%), already live in today's code, no switch needed. Unlike the player-side stack, this one only needs ~4 items (hand-authored BESTIARY equipment, not a dynamically-equipped loadout), so slot limits don't rule it out. **Still, -41% is UNDER the proposed 60% cap (floor ×0.4)** -- not a violation, just a real multi-factor stack worth having on record.
**Net correction (18 Nov): neither chain exceeds the proposed 60% cap today.** The player-side worst case lands exactly at the cap (×0.4, not past it); the enemy-side worst case (×0.59) is comfortably under it. No sign-off needed before 2d on this front -- R3's incoming-mitigation cap introduces no regression anywhere that's actually buildable. (Process note: future worst-case stack claims in this catalogue must be checked against EQUIP_SLOT_CAPACITY/EQUIP_SLOTS -- 11 total equipped items -- before being reported as "achievable today," not just checked for which sets/effects exist.)

Tyler's flag: R1 (ally holders) and R2 (enemy holders) widen WHO an entry's `holders` list includes, but that's moot if the number itself is still computed by a helper hardcoded to read `state` (the player) no matter who the registry says can hold it. Every function below is "the single place a given number is decided" (js/data/sets.js's own header comment for its block) — migrating the registry entries without also generalizing these is a trap: the entry would say `holders: ["player","ally","enemy"]` but the value behind it would still only ever be the player's.

Every one of these needs its `state` parameter generalized to whichever holder is asking (and its internal `hasEffect(state, ...)`/`hasSetTier(state, ...)` calls updated to match) before R1/R2 can reach anything it governs.

**Partially generic already (inconsistent — some call sites pass a real holder, others still hardcode `state`):**
