Combat Rebuild Phase 1, step 1d: migrate ally-attacks-enemy onto the pipeline
Moves the ally-to-enemy damage path onto the five-step pipeline
(chooseAction/chooseTargets/rollToHit/calculateDamage/applyAndReact),
same shape steps 1b/1c used for the enemy-side paths. Two structurally
different shapes share the new actor.kind === "ally" branches:

  - allyAggressiveActionLegacy (combat.js) -> allyAggressiveAction
    (pipeline.js): the plain-ally path (Kessa today) -- banked enemy-
    Defense consumption (Brace/Guarded Strike/Sure Foundation), Opening
    Reach/Executioner multipliers, sangCuDefenderMitigation, and a miss
    provoking the enemy's own Riposte (riposteCounterByEnemyOnAlly).
  - basicCompanionAttackLegacy (companion.js) -> basicCompanionAttack
    (pipeline.js): a kit-bearing ally's fallback swing.
  - useHadrianActiveLegacy's Crushing Blow/Groundbreaker direct-damage
    tail -> resolveHadrianActiveDamage (pipeline.js), called from the
    live useHadrianActive (companion.js) for the PRIMARY target only;
    Groundbreaker's splash stays in useHadrianActive's own loop, reusing
    the primary hit's baseAtk/splashAtkMult (no separate hit roll of its
    own, so it isn't a second pipeline target). useHadrianActive's
    taunt/heal/ultimate branches are untouched -- they deal no damage,
    so they're outside the pipeline's scope -- but re-verified against
    useHadrianActiveLegacy anyway for regression safety since both got a
    large edit in this same commit.

Confirmed while reading the code line by line, NOT assumed: Hadrian's
two shapes have NONE of Kessa's five extras above -- no banked-Defense
read, no Opening Reach, no sangCuDefenderMitigation, no Riposte-on-miss.
A real, pre-existing asymmetry between the two ally-attack shapes,
preserved exactly rather than unified -- documented in pipeline.js's own
header; out of scope for tools/combat_asymmetry_register.md, which is
specifically about the enemy-attacks-player vs enemy-attacks-ally axis,
not this one.

stat() (combatant.js), per the stat()-purity hard rule:
  - ally "atk"/"acc": centralized via new effectiveAllyAtk/
    effectiveAllyAcc (companion.js) -- pure extracts of
    allyAggressiveActionLegacy's own inline calc, zero behavior change.
    This is ONLY the plain-ally formula; a kit-bearing ally's atk/acc
    (ally.atk + hadrianFlatAtkBonus(ally); raw ally.accuracy) never went
    through allyBuffStatTotal/allyStatusStatTotal/atkPct at all, so it
    stays a separate, kit-specific calculation inline in the pipeline's
    ally-actor branches -- folding it into stat() would have silently
    added buffs/statuses to Hadrian's attack that never applied before.
  - enemy "def": centralized as the PURE creature.def only, no banked
    bonus. allyAggressiveActionLegacy used to zero Brace/Guarded Strike/
    Sure Foundation's banked Defense (and immediately re-grant Sure
    Foundation if the enemy still wears it) BEFORE computing damage;
    that one-shot consumption now happens once, in applyAndReactAllyActor
    (step 5), after calculateDamage has already used the PEEKED value --
    nothing re-reads the fields in between, so the computed number is
    identical either way. This was possible to do cleanly, so it was
    done, per the handoff's own instruction -- no behavior-change
    exception needed here, unlike U1's matchup gap.
