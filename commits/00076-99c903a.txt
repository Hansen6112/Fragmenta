Step 1h-iv §4: delete wireActiveEnemyProxy -- PER_ENEMY_FIELDS proxy fully removed
The last call sites were rewritten in d12c186; this commit deletes the
proxy constructor itself and its one call site in startCombat, completing
step 1h-iv. PER_ENEMY_FIELDS (the field-name list) stays -- it's still a
live reference, both for activeEnemySlot's own neighboring comment and
for the 6 Layer 1 parity test files' snapshot() flattening (below).

Two things found while confirming the deletion was genuinely clean, not
just passing tests by coincidence:

1. state.combat's own object literal (in startCombat) carried a stray
   `reinforcedAttackCount: 0` data property -- a leftover default seed
   that predates the multi-enemy refactor. While wireActiveEnemyProxy was
   still wired, Object.defineProperty silently replaced it with the
   accessor on the same tick, so it was never visible. Once the proxy
   was gone, this would have made `state.combat.reinforcedAttackCount`
   quietly return 0 instead of genuinely being undefined -- the real
   "stale value, not a clean break" risk the handoff flagged for this
   step, just arrived from the literal rather than from the proxy's own
   construction. Removed; the real per-enemy initializer two lines
   earlier in the same function (enemies.map(...)) is untouched and was
   always the one that mattered.

2. Deleting the proxy changes what JSON.stringify(state.combat) produces
   again, the same way deleting wirePlayerFieldsProxy did in 1h-iii: the
   24 PER_ENEMY_FIELDS entries stop being enumerable top-level keys on
   combat. The 6 Layer 1 parity files' snapshot() functions already
   reconstruct the pre-1h-iii flat shape for .player; extended the same
   function in each to also copy the active enemy's own PER_ENEMY_FIELDS
   values back onto the flattened copy (by name, not a wholesale object
   merge, since the enemy record also carries fields -- alive,
   counterGuardUsedThisRound, ... -- that were never part of the old
   flat alias and must not leak into the comparison). Verified this was
   actually necessary, not just precautionary, by running the suite
   before writing the fix and confirming exactly these 6 files'
   PARITY-tagged scenarios failed; re-ran after and confirmed the
   expected 445/445 with no further changes needed elsewhere.

Verified with a direct in-page check (new GameState, startCombat,
