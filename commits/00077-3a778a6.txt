tools/combat_field_ledger.js: regenerated to 0 fields left to move --
first time this Phase. Two real bugs in the ledger's own text-scan
found and fixed first, both confirmed by actually running it and
inspecting the output before trusting the number:

1. The field/callee scan never stripped comments. Through 1g-vii this
   never mattered (every tracked field still had a real call site, so
   a comment mentioning the same spelling was redundant with a genuine
   hit); step 1h's own rename pass exposes it, since a left-behind
   EXPLANATORY comment describing old behavior (kept on purpose, as
   history -- e.g. combat.js's "mirrors combat.lastDamageType") is now
   the ONLY text left that matches, for 6 fields that have zero real
   callers. Fixed by stripping block and line comments before the scan,
   the same way tools/audit.js's own P1/P3 rules already do.

2. The bare `combat\.(\w+)` field-capture regex wrongly grabbed
   "player" itself out of combat.player.<realField> chains, adding a
   phantom tracked field. A straightforward (?!\.) negative-lookahead
   fix made it WORSE, not better -- it doesn't fail the whole match,
   it just lets the greedy quantifier backtrack one character short
   (confirmed by running it: "cooldowns"/"downs"/"enemies"/"player"
   came out truncated to "cooldown"/"down"/"enemie"/"playe" in the
   tracked table). Fixed by adding \b before the lookahead, which
   forces the match to fail cleanly at the only identifier boundary
   that exists, instead of backtracking into a wrong one.
