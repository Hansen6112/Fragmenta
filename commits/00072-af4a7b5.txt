Combat Rebuild Phase 1, step 1h-iii's last commit: the alias is gone.
combat.player is an ordinary, enumerable state.combat key now (same
status as enemies/activeIndex), exactly like every other PLAYER_FIELDS
access is already written to expect.

Two real bugs found and fixed while landing this, both caught by
actually running the full verification pass rather than assuming the
mechanical batches covered everything:

1. Two dynamic bracket-notation call sites my batches' literal-name
   regex couldn't match (js/engine/combat.js and pipeline.js, both the
   same Avatar of Chaos mechanic -- one random stat's Bonus field
   built as a string and indexed): `state.combat[field]` was still
   reading/writing a field name computed at runtime. Re-pointed both
   to state.combat.player[field] -- confirmed via a full-repo grep for
   any remaining `.combat[` bracket access against a variable, which
   found exactly these two in production code (plus 8 more in
   tools/tests/, one of them step 1h-iii's OWN freshly-written
   ROUNDTRIP-01 tests, which use BATCH_FIELDS.forEach with a loop
   variable the same way -- all 8 fixed the same way).

2. The real bug: deleting wirePlayerFieldsProxy's accessor layer
   without separately deleting the flat data properties it used to
   REPLACE (via Object.defineProperty, which has the same practical
   effect as a delete) left every PLAYER_FIELDS entry's ORIGINAL,
   frozen fight-start value sitting on combat itself, stale and fully
   disconnected from combat.player -- silently returning a stuck
   initial value to anything that still read the old spelling, not
   undefined. The handoff's own stated proof condition ("accessing the
   old way should return undefined") is exactly what this would have
   broken. Fixed by having makePlayerCombatStore delete each field off
   combat right after copying its value into the store. Caught by the
   four P1G-*-ACCESSOR-01 tests (rewritten this commit to check the
   new reality -- plain data properties on combat.player, absent from
   combat itself -- since their old premise, real get/set accessors
   directly on combat, is the exact thing step 1h-iii replaces) failing
   until this fix landed.

Also fixed, disclosed: the Layer 1 parity harnesses' own snapshot()
helpers (phase1_step1b/1c/1d/1e_i/1e_ii/1e_iii) broke a second time
once combat.player became enumerable and the flat accessors
disappeared -- the frozen pre-1h fixtures can never be re-captured
(their oracle functions are gone since step 1h-ii), so snapshot() now
permanently reconstructs the old flat shape (merging .player back up,
dropping the key) for DATA equivalence, and snap comparisons go
through a stable (sorted-key) re-serialization for order equivalence,
since the two representations' own property insertion order can never
match again. phase1_step1d/1e_i/1e_ii/1e_iii already had their own
sortedStringify and only needed the data fix; 1b/1c got both.
