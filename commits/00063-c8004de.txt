Caught during verification, fixed before committing: the Layer 1
parity harnesses' own snapshot(s) helper (phase1_step1b/1c/1d/1e_i/
1e_ii/1e_iii) does `JSON.stringify({ ..., combat: s.combat })` and
string-compares it against each scenario's frozen pre-1h fixture.
Making combat.player enumerable (the first version of this commit)
changed that JSON's shape -- the exact same 130 values appearing a
second time, nested -- so every one of those files' scenarios failed
on a snap mismatch despite the game's actual observable behavior
(narrative lines, numeric outcomes) being provably identical
(snapDiffHint showed the new snap ~3200 characters longer than the
frozen one, consistent with one extra nested copy of the same data,
nothing else). Making combat.player non-enumerable instead keeps
JSON.stringify(state.combat) byte-identical to its pre-1h-iii shape
for as long as the compat accessors exist alongside it, so the frozen
fixtures stay valid without touching any of those six test files.
